# MirasAI 0.14.0

Menys crides per fer la mateixa feina. Surt de refer pàgines senceres en un web
real amb la 0.13.0 (troballes F-045 a F-048 de
[`yootheme-builder-findings.md`](../yootheme-builder-findings.md)): una pàgina de
quatre seccions va costar uns vuit minuts, a tres processos per canvi.

Dues eines noves al host, una al router, un error corregit a WordPress i
respostes que diuen més. Res del que ja hi havia canvia d'esquema ni deixa de
funcionar.

## Diversos canvis en una sola escriptura (F-046)

- **`template/element-replace-children`** substitueix tots els fills d'un element
  en una escriptura: les seccions d'una pàgina amb `path` `root` (per defecte), o
  les files d'una secció, les columnes d'una fila, els elements d'una columna. La
  previsualització llista què se'n va i què hi entra. Cada fill nou passa les
  comprovacions de `template/element-add`, `layout` de les files inclòs. Si es
  canvien les columnes d'una fila i el seu `layout` ja no les descriu, torna
  l'avís `row_layout_mismatch`.
- **`template/element-batch`** aplica diverses operacions a un layout amb un sol
  `if_match`: una lectura, una previsualització i una escriptura. Cada operació
  porta `op` (`add`, `update_props`, `move`, `clone`, `delete`,
  `replace_children`, `source_set`, `source_delete`) i els arguments de la seva
  eina. Van en ordre i cadascuna veu el layout com l'han deixat les anteriors.
  Tot o res: si una falla no s'escriu res, i l'error diu quina. Fins a 100
  operacions.
- **`new_etag`** ja el tornaven totes les escriptures i és l'etag de la lectura
  següent. Ara està escrit: encadena'l com a `if_match` i no rellegeixis el
  layout entre escriptures.

```json
{
  "post_id": 12,
  "if_match": "…",
  "dry_run": true,
  "operations": [
    {"op": "delete", "path": "root>section[3]"},
    {"op": "update_props", "path": "root>section[0]>row[0]", "props": {"layout": "1-2,1-2"}},
    {"op": "add", "after_path": "root>section[0]", "element": {"type": "section", "children": []}}
  ]
}
```

## Camins que no resolen (F-045)

L'índex d'un segment compta la posició dins del pare, no dins del tipus:
`text[2]` és el tercer fill, hi hagi el que hi hagi abans. Un camí que no resol
torna, a més del codi de sempre (`element_not_found`, `parent_not_found`,
`reference_not_found`, `target_parent_not_found`):

- `resolved_path` i `failed_segment`: fins on ha resolt i on s'ha aturat;
- `available_children`: els camins que hi ha en aquell punt;
- `did_you_mean`, quan es pot deduir llegint l'índex com «l'n-è fill d'aquest
  tipus». És una suposició: cal comprovar-la abans d'escriure-hi.

Val per a les eines de lectura i d'escriptura que reben un camí.

## El text pla de la pàgina (F-047)

YOOtheme desa, al costat del layout, una versió en HTML pla: davant del
comentari a `post_content` a WordPress i a `introtext` a Joomla. El visitant no
la veu; la cerca i els plugins de SEO sí. Les escriptures per MCP la deixaven
com estava. Ara la regeneren amb el Builder del web, com fa el Builder en desar,
i la resposta ho diu a `fallback_content`:

- `regenerated`: el text pla torna a coincidir amb el layout;
- `stale`, amb el motiu: YOOtheme no l'ha pogut pintar en aquella petició, o no
  s'ha pogut desar, i hi queda l'anterior fins que la pàgina es desi una vegada
  al Builder. A Joomla passa amb els layouts que tenen fonts dinàmiques. El
  layout ja està escrit en tots dos casos.

Una pàgina que queda sense text (buida, o només amb elements que no en tenen)
dona `regenerated` amb longitud 0.

## Errors corregits

- **WordPress (F-048).** En escriure una pàgina o entrada, un `$` seguit de
  xifres (`$10`) o una barra invertida en qualsevol element del layout es podien
  perdre, encara que el canvi fos en un altre element. Passava a totes les
  versions anteriors. Les plantilles i els widgets no hi queien.
- **`template/element-move` amb `target_parent_path`.** El destí es buscava
  després de treure l'element del seu lloc, de manera que un destí que penjava
  d'un germà posterior de l'element quedava un índex més enllà: no es trobava, o
  es trobava un altre element. Ara es llegeix al layout que ha llistat qui
  crida, com ja feien `before_path` i `after_path`.

## Router

- **`mirasai/batch`** fa diverses crides independents contra un web en un sol
  procés i torna cada resultat en ordre: llegir set layouts costa una arrencada
  i no set. S'atura a la primera crida que falla, tret que `stop_on_error` sigui
  `false`. El host comprova cada crida com si anés sola. Cada resultat porta el
  contingut desempaquetat a `result`; si el host ha tornat més d'una part, o
  imatges, també hi són totes a `content`.
- El router demana la llista d'eines a cada host una vegada per procés, no abans
  de cada crida.

## Què té cada entorn

- Les eines `template/element-*` i `fallback_content` són del host: les té el
  host per HTTP, mcp2cli apuntat al host i el router, que les passa tal qual.
- `mirasai/batch` és del router.

## Validació

- Proves locals: `docker/test-yootheme-element-batch.php` (102 comprovacions,
  els dos hosts) i `packages/mirasai-mcp/test/batch.test.mjs`. `npm test` sencer
  en verd.
- En directe, amb crides MCP als dos webs de proves (WordPress 7.1.4 amb YOOtheme
  5.0.53 i Joomla 6.2 amb YOOtheme 5.0.54): 24 comprovacions a cadascun. Refer
  una pàgina, un lot de quatre operacions, `new_etag` igual a l'etag de la
  lectura següent, un camí equivocat amb la seva proposta, un lot que falla sense
  escriure res, el text pla regenerat (també buit, en buidar la pàgina), un
  moviment cap a un destí que penja d'un germà posterior i l'avís en canviar les
  columnes d'una fila. A WordPress, a més, la pàgina vista com a visitant i la
  cerca.
- `mirasai/batch` només té proves locals.
