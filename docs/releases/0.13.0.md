# MirasAI 0.13.0

Avisos que van sortir de fer servir la 0.12.0 en webs reals (troballes F-040 a
F-044 de [`yootheme-builder-findings.md`](../yootheme-builder-findings.md)). Cap
eina nova i cap canvi d'esquema: les eines que ja hi havia diuen més coses, i
`template/element-add` omple un camp que abans quedava buit. Res del que ja hi
havia deixa de funcionar.

Tot és del host: ho tenen el host per HTTP, mcp2cli apuntat al host i el router,
que ho passa tal qual.

## Files amb columnes que el Builder veu com a «Whole» (F-044)

Una fila escrita per MCP amb només `width_medium` a les columnes es veia bé al
web, però al Builder sortia com a «Whole», amb les columnes mal dibuixades, i
«Edit layout» n'hauria reiniciat les amplades. El web pren les amplades de cada
columna; el Builder llegeix el `layout` de la fila (`3-4,1-4`, o
`1-4,1-4,1-4,1-4|1-2,1-2,1-2,1-2` amb `width_small` darrere de `|`).

- **`template/element-add`** posa `layout` a una fila nova quan les amplades de
  les columnes són les d'un layout del Builder, i ho diu a `row_layout_filled`.
  Si no ho són, no endevina res: torna l'avís `row_layout_mismatch`. També avisa
  quan una columna nova deixa desquadrada la fila on va.
- **`template/element-update-props`** avisa (`row_layout_mismatch`, amb el
  `layout` que cal posar) quan un canvi de `width_*` d'una columna o del
  `layout` d'una fila els deixa desquadrats. Els altres props no avisen.
- **`template/audit`** troba les files que ja estan així, també amb
  `scope: "site"`, i proposa el valor.

Una fila de columnes sense cap amplada no s'avisa: el web i el Builder la
mostren igual, a pila.

## Plantilles d'arxiu i fonts que no es pinten (F-040)

`template/render-check` torna `warnings`:

- `listing_not_reproducible` en una plantilla d'arxiu, cerca o taxonomia: fora
  d'una petició d'aquell tipus, la consulta no té entrades i el resultat només
  ensenya el que és estàtic. Per a aquestes plantilles, la prova és
  `site/public-fetch` a una URL d'aquell tipus.
- `dynamic_not_rendered`, amb els paths dels elements lligats a una font que no
  s'han pintat. Un element desactivat, o dins d'una branca desactivada, no hi
  surt: no es pinta perquè algú l'ha desactivat, no perquè la font no doni res.

## Condicions sobre un camp llista (F-042)

`template/element-source-preview` torna `binding_through_list_field` quan una
propietat o una condició passa per un camp que és una llista (una galeria
d'ACF, `categories`, `tags`). YOOtheme el deixa buit fora d'un element que es
repeteix sobre aquella llista, i una condició `!!` hi amaga l'element a totes
les pàgines.

## Extractes sense límit en un llistat (F-043)

`template/audit` dona `unbounded_teaser` (notice) quan un ítem de llista mostra
`teaser` o `content` sense el filtre `limit`: una entrada sense extracte surt
sencera a cada targeta.

## Playbook

- `preview_token` prova que la confirmació porta els mateixos arguments que la
  previsualització; no caduca. Que la previsualització encara valgui ho
  garanteix `if_match` (F-041).
- Anti-loop `row_layout_whole_in_builder` per al cas de la F-044.

## Repositori

Els documents, el README, els comentaris del codi i les proves ja no nomenen
clients, els seus dominis ni el servidor: el repo és públic. El comportament no
canvia.

## Provat i no provat

A més de `npm test`, provat als dos webs de proves (WordPress 7.1.4 amb
YOOtheme 5.0.53; Joomla 6.2.0 amb YOOtheme 5.0.54):

- una fila `3-4`/`1-4` a WordPress i una `1-3`/`2-3` a Joomla queden desades amb
  el `layout`, i treure'l avisa en la mateixa escriptura;
- l'auditoria troba la fila, i la correcció que proposa la deixa neta;
- una plantilla d'arxiu dona els dos avisos de `render-check`;
- `categories` (WordPress) i `tags` (Joomla) donen
  `binding_through_list_field`, i `title` no;
- un ítem amb `teaser` sense límit dona `unbounded_teaser`.

No provat: la pantalla del Builder en un navegador després d'una escriptura. El
`layout` desat és el que escriu el JavaScript del Builder i el que tenien les
files refetes a mà al web on es va trobar el problema.
